      Tugas Akhir · Capstone Design — S1 Teknik Telekomunikasi, Telkom University

      Memantau solar genset STO: akurat untuk tiap bentuk tangki, hemat energi saat mengirim data.

      Cetak biru pengembangan Fuel Tank Management (FTM), sistem IoT (Internet of Things, perangkat yang mengirim data lewat internet) untuk memantau BBM genset di STO. FTM lahir dari Kerja Praktik di PT Telkom Infrastruktur Indonesia (TIF/InfraNexia) Area Pasuruan dan kini dipakai dalam pilot terbatas. Halaman ini merangkum masalahnya, kondisi sistem sekarang, dan rencana TA.

      01Masalah

      Kelihatannya sepele, dampaknya tidak

      STO harus menjaga availability (ketersediaan layanan) sekitar 99,99%. Saat PLN padam, baterai menahan beban sebentar, lalu genset berbahan bakar solar mengambil alih. Solar adalah pertahanan terakhir, tetapi selama ini isinya diketahui dengan cara manual, berisiko, dan tanpa data.

        Simulasi: kapan solar benar-benar terpakai?

        Pilih skenario untuk melihat aliran daya, kapan genset menyala, dan mode kirim FTM 2.0.

        Geser diagram ke samping untuk melihat seluruhnya.

        Tangki harian–

        “Bukankah Telkom sudah punya prosedur, dan petugas sudah tahu kapan harus isi ulang?” Benar. Karena itu nilai FTM bukan menggantikan penilaian petugas, tetapi menghapus pengukuran yang berisiko, memberi visibilitas banyak STO sekaligus, dan menghasilkan data untuk audit dan perencanaan.

        02Titik awal

        FTM v1 sudah berjalan: TA berangkat dari pilot nyata

        Dalam ±2–3 minggu, FTM v1 dibangun ulang dan dipakai di lapangan: sensor ultrasonik → ESP8266 → API berkunci → MySQL cloud → dashboard web dan Telegram. Biaya cloud selama pilot praktis Rp0 karena memakai kuota gratis. Nama perangkat, lokasi detail, dan kredensial sengaja tidak ditampilkan.

          Linimasa proyek

          Dari chat grup dan riwayat repositori. Titik amber = tonggak penting.

            Apa yang sudah terbukti

            • Alur ujung-ke-ujung dengan perangkat nyata di beberapa STO, bukan sekadar demo.
            • Rollup 5 menit: 239.945 sampel diringkas menjadi 16.195 baris (±14,8×).
            • Provisioning berbasis persetujuan, sehingga perangkat asing tidak bisa langsung masuk.
            • 160 tes otomatis, CI, dan proteksi branch utama.
            • Kolaborasi dengan engineer lapangan yang paham hardware dan catu daya.

            Celah yang menjadi ruang TA

            • Akurasi belum dikalibrasi dan belum diuji per model tangki.
            • Perangkat mengirim dengan interval tetap, Wi-Fi tidak pernah tidur.
            • Kuota cloud gratis mulai habis pada 24 Agustus.
            • Belum ada konteks PLN/genset, sehingga penurunan level belum punya makna.
            • Kode makin sulit direview, dan rahasia pernah tersebar di chat.

            05Inti TA

            Tiga pilar, masing-masing menjadi pertanyaan riset yang bisa diukur

            Arahan dosen: meningkatkan akurasi data ketersediaan BBM untuk berbagai model tangki, mencari model transmisi data demi penghematan energi, dan mengkaji sistem yang efektif-efisien dari berbagai aspek. Setiap pilar punya konsep, simulator untuk berpikir, dan eksperimen untuk membuktikan.

            RQ1 · Akurasi

            Seberapa akurat estimasi volume untuk berbagai geometri tangki setelah kalibrasi dan kompensasi suhu, dibanding v1?

            RQ2 · Energi & transmisi

            Berapa penghematan pesan, byte, dan energi dari telemetri adaptif dibanding interval tetap, tanpa kehilangan kejadian penting?

            RQ3 · Efektif-efisien

            Arsitektur mana yang paling seimbang dari sisi biaya, keamanan, keandalan, dan skalabilitas untuk 29 STO sampai skala nasional?

              Kalkulator akurasi volume

              Ubah suhu, salah ukur pemasangan, dan kemiringan sensor. Lihat berapa liter selisihnya.

                Simulator telemetri 24 jam

                Bandingkan strategi kirim pada hari yang sama: pesan, byte, energi, latensi deteksi kejadian, dan umur baterai.

                Anatomi payload: v1 vs ringkas

                Ukuran byte dihitung langsung di browser dari contoh payload (nilai disamarkan).

                  Kalkulator kuota cloud (Vercel Hobby)

                  Kenapa kuota hampir habis di Agustus, dan berapa ruang yang tersisa dengan telemetri adaptif?

                    09Teknologi

                    Stack dan struktur repositori

                    Membandingkan FTM v1, proyek CoE BHT, video “Tech Stack 2026”, dan rekomendasi TA. Tujuannya bukan memakai yang paling baru, tetapi yang paling mudah dirawat tim 2 orang, portabel bila kelak di-host internal Telkom, dan bernilai di pasar kerja.

                    LapisanFTM v1CoE BHTVideo PZNRekomendasi

                    Struktur monorepo yang diusulkan

                    ftm-next/
├─ apps/
│  ├─ web/          # Next.js: dashboard, admin, installer
│  └─ api/          # Hono: ingest + policy, auth perangkat
├─ packages/
│  ├─ core/         # geometri, kalibrasi, kualitas, kejadian
│  ├─ db/           # skema Drizzle + migrasi
│  └─ contracts/    # skema Zod payload & policy
├─ firmware/         # PlatformIO ESP32: mesin status, buffer
├─ experiments/      # notebook Python + data E1–E8
├─ infra/            # docker-compose untuk self-host
└─ docs/             # ADR, runbook, serah terima

                    Tentang video dan alat yang dirujuk

                    Video “Tech Stack 2026” (Programmer Zaman Now): TypeScript, Svelte + Bun di frontend, Bun + ElysiaJS + Drizzle di backend. Yang diambil: TypeScript dan Drizzle. Bun boleh untuk tooling. Untuk API dipilih Hono karena berjalan di Bun maupun Node, jadi tidak terkunci ke satu runtime.

                    CoE BHT: NestJS dan Next.js di repo terpisah, PostgreSQL + Drizzle, Better Auth, Infisical. Yang diambil: Drizzle, Better Auth, disiplin pengelolaan rahasia. Yang tidak: polyrepo dan NestJS, terlalu berat untuk tim 2 orang dengan API kecil.

                    Archify: bagus untuk diagram proposal dan slide, bukan fondasi website.

                    “Rebuild dari nol” berarti kode baru yang bersih, tetapi v1 tetap melayani lapangan sampai v2 terbukti.

                    10Pembuktian

                    Delapan eksperimen dengan hipotesis, alat ukur, dan kriteria berhasil
